# Отчёты об ошибках: контракт с `POST /api/report`

Приёмник существует и отвечает, а его исходник доступен, поэтому всё описанное ниже
**прочитано в коде** приёмника, а не выведено из формы ответов: `server.mjs`
(функции `normalizeReport`, `readJson`, `rateOk`, `buildView`, `makeMongoStore`,
`makeFileStore`), его `config.json` и `README.md`. Документ описывает две половины
одного провода: что приёмник принимает и как плагин (`lib/errors.js`, `lib/net.js`)
заполняет его поля. Автору монитора достаточно этого файла — читать исходник плагина
не нужно.

Там, где код расходится с прежним описанием, построенным на пробах, это сказано
прямо. Расхождений три, и все они в пользу точности: правило отказа `400` известно
дословно, превысивший предел `meta` отбрасывается целиком, а не обрезается, и
картина строится по времени получения отчёта, а не по времени события.

Адрес по умолчанию: `http://185.75.189.247:3789/api/report` — общий публичный
приёмник, один на все установки. Метод `POST`,
`content-type: application/json`, тело — **один плоский объект**. Конверта и массива
событий нет: один отчёт — один POST.

## Зачем это существует

Монитору нужно три факта: **когда** модель перестала отвечать, **у скольких людей**
одновременно и **что именно** сломалось. Обычный способ их получить — зонд:
отдельный запрос к модели по расписанию. У зонда две беды: он сжигает токены на
запросы, которые никому не нужны, и он отвечает за одного человека — за того, на
чьей машине запущен, поэтому «сайт лежит» и «у меня не работает» для него
неразличимы.

Вместо зонда используются **пассивные отчёты**. Плагин и так знает исход каждого
запроса к модели, который сделал пользователь, и сообщает только о сбоях
инфраструктуры. Один сбой — один отчёт, в котором есть момент, модель, вид сбоя,
статус, длительность и очищенный текст ошибки.

Отсюда два следствия, важных для приёмника. Отчёты приходят **пачками и задним
числом**: всякий раз, когда отправить не удалось — приёмник занят или лежит, машина
пользователя не в сети или спала, — отчёты накапливаются в очереди на диске и после
восстановления приезжают разом, со своими исходными метками времени, которым может
быть несколько часов или дней. Приёмник при этом живёт не там же, где API
провайдера, поэтому авария провайдера сама по себе не мешает отчётам дойти; мешают
ей только собственный простой приёмника и отсутствие сети у пользователя. И отчёты
**не требуют аутентификации**: плагин не отправляет ни ключей, ни заголовка
`Authorization` никогда.

## Что отправляется и когда

**Ошибка** отправляется только тогда, когда она инфраструктурная: соединение не
состоялось, DNS не разрешился, сокет отказал или оборвался, TLS не собрался, шлюз
провайдера ответил 5xx или 404, ответ не пришёл за отведённое время. Решение
принимает `classifyFailure`, и оно же отвечает за то, чего в отчёте не будет вовсе:
кончившаяся подписка, исчерпанная квота или баланс, неверный либо отсутствующий
ключ, rate limit, не поместившийся контекст, прерванный пользователем запрос,
неизвестная модель и любая другая ошибка запроса, которую harness помечает
собственным кодом. Это положение конкретного пользователя, а не состояние сервиса,
и в мониторе оно выглядело бы как авария на ровном месте.

**Успех не отправляется никогда.** Приёмник принимает ошибки, и успешный запрос —
не событие для него. Успех выполняет две локальные задачи: считается для страницы
настроек, чтобы было видно, что плагин жив и смотрит, а не молча простаивает, и
немедленно отправляет ещё не закрытую свёрнутую ошибку той же модели. Именно
второе даёт монитору метку восстановления: отчёт о сбое приезжает в момент, когда
модель снова ответила, а не по окончании окна свёртки.

Отправка не блокирует запрос и не может его уронить: очередь живёт в памяти и на
диске, таймер не держит процесс, а любая ошибка внутри отчётности проглатывается.

## Поля приёмника

Все поля необязательны, кроме одного правила: должно присутствовать хотя бы
`message` или `code`. У большинства полей есть синонимы — это варианты одного
хранимого столбца, а не дополнительные поля.

| Поле (синонимы) | Тип | Смысл |
|---|---|---|
| `message` (`error`, `detail`) | string | текст ошибки, обрезается до **2000** символов |
| `code` (`type`, `kind`) | string | тип ошибки, обрезается до **120**; при отсутствии приёмник подставляет `UNKNOWN` |
| `plugin` (`source`) | string | какой плагин прислал, до 120; при отсутствии `unknown` |
| `version` | string | версия плагина, до 60 |
| `provider`, `model` | string | провайдер и модель, до 120 каждое |
| `status` | int | HTTP-статус, **если он есть**; не-целое становится `null` |
| `ts` (`timestamp`) | number | время клиента в миллисекундах; сохраняется как `clientTs` |
| `meta` | object | дополнительные данные; принимается, только если его `JSON.stringify` не длиннее **8192** символов |

Неизвестные поля на верхнем уровне приёмник игнорирует и отвечает `200`, так что
добавление поля в будущем не сломает доставку.

### Что приёмник делает с телом

Всё ниже прочитано в `normalizeReport` из `server.mjs`, а не выведено из ответов.
Синонимы разбираются через `??` в порядке, указанном в таблице, поэтому **первый
непустой выигрывает** — это и есть причина правила «один синоним на понятие»:
прислав `message` и `error` рядом, отправитель не выбирает, что сохранится, а
оставляет выбор приёмнику.

Три детали, которые меняют представления отправителя.

**Отказ `400` наступает ровно в одном случае**: когда `message` пуст **и** `code`
оказался равен `UNKNOWN` (то есть не был прислан вовсе). Всё остальное принимается,
включая отчёт без модели, без статуса и без `ts`.

**Превысивший 8192 символов `meta` не обрезается, а выбрасывается целиком** —
приёмник сохраняет вместо него `null`. Молча, с ответом `200`. Для отправителя это
означает, что раздутый `meta` теряет не часть данных, а все, включая то единственное
поле, ради которого `meta` и существует.

**`status` принимается как `Number.isInteger(+b.status)`, и ноль — целое число.**
Присланный `status: 0` сохранился бы как `0`, а не как «статуса не было», и попал бы
в агрегаты как настоящий HTTP-статус. Отсутствующее поле становится `null`. Это
делает наше решение не отправлять ноль не вопросом вкуса, а единственно верным.

**Обрезка на стороне приёмника короче нашей.** Плагин ограничивает строковые поля
128 символами, а `normalizeReport` режет `code`, `plugin`, `provider` и `model` до
120, а `version` — до 60. Сегодня расхождение не имеет значения: значения `code`
берутся из фиксированного словаря, где самое длинное — `connect_timeout`, — id
моделей приходят из каталога провайдера, а версия плагина короткая. Но это именно
расхождение, а не совпадение, и оно молчаливое: поле длиннее 120 символов доедет
обрезанным, с ответом `200`, и узнать об этом можно только сравнив отправленное с
сохранённым. Тому, кто добавит длинный вид сбоя или начнёт присылать составной id
модели, стоит сначала укоротить наш предел до их.

Сохранённый документ выглядит так — это схема и для MongoDB, и для файлового
хранилища:

```
{ plugin, version, provider, model, code, message, status, meta, clientTs, serverTs, ip }
```

`serverTs` приёмник ставит сам (`Date.now()`), `ip` берёт из `x-forwarded-for`, а
при его отсутствии — из адреса сокета. Индексы в MongoDB созданы по `serverTs` и по
паре `(code, serverTs)`. История обрезается до 45 дней по `serverTs`, но **только в
файловом хранилище**, которое фильтрует строки при каждом сохранении; в MongoDB не
удаляется ничего.

Отдельно стоит запомнить, что `clientTs` сохраняется, но **не используется**
агрегацией: картина строится по `serverTs`. Подробности и следствия — в разделе
«`ts` может быть намного старше доставки» ниже и в
[docs/uptime-view.md](<uptime-view.md>).

## Как плагин их заполняет

Один синоним на понятие, всегда. Плагин отправляет `message`, `code`, `plugin`,
`ts` и никогда не отправляет рядом `error`, `detail`, `type`, `kind`, `timestamp`
или `source`. Причина теперь известна из кода: `normalizeReport` разбирает синонимы
цепочкой `message ?? error ?? detail`, и при двух присланном одновременно сохранится
тот, что стоит в цепочке раньше, — то есть выбор сделает не отправитель, а получатель,
и не заметит этого.

| Поле приёмника | Значение плагина |
|---|---|
| `plugin` | `dsh-rustvy`, всегда |
| `version` | версия плагина из `package.json` |
| `provider` | маршрут провайдера: `rustvy`, `rustvy-k2`, … |
| `model` | id модели; `unknown`, если определить не удалось |
| `code` | **наш вид сбоя** (`connect_timeout`, `upstream_502`, …) — см. ниже |
| `status` | HTTP-статус; **поле отсутствует**, когда статуса не было |
| `message` | очищенный текст ошибки, до 2000 символов; никогда не пустой |
| `ts` | момент события в миллисекундах, а не момент отправки |
| `meta.id` | uuid установки |
| `meta.ms` | длительность запроса в миллисекундах |
| `meta.n` | сколько событий свёрнуто в отчёт; отсутствует, когда одно |
| `meta.harnessCode` | код ошибки, каким его дал harness |
| `meta.t` | тот же момент события, что и `ts` |

Четыре решения стоит объяснить отдельно.

**В `code` — наш вид сбоя, а не код harness.** Монитор группирует по вопросу
«какие ошибки падали на данной модели», и `upstream_502` на него отвечает, а
`PI_AI_ERROR` — нет: под этим кодом одинаково живут и отказ соединения, и ответ
шлюза, и оборванный поток. Вердикт harness при этом не теряется, он переезжает в
`meta.harnessCode`. Если автору приёмника нужна в `code` собственная таксономия —
в его примере стоит `INVALID_REQUEST`, то есть как раз код harness, — замена
делается в одну строку в `reportPayload`, и строка помечена комментарием.

**`status` отсутствует, а не равен нулю.** У тайм-аута соединения HTTP-статуса нет
вовсе, а ноль — не статус. Теперь это подтверждено кодом, а не только пробой:
приёмник хранит статус как `Number.isInteger(+b.status) ? +b.status : null`, и
`+0` — целое, так что присланный ноль лёг бы в хранилище числом `0` рядом с
настоящими статусами и рано или поздно попал бы в агрегат. Отсутствующее поле
становится `null`, что и означает «статуса не было». Длительность при этом не
теряется: она лежит в `meta.ms`.

**`meta.id` — единственное место для uuid установки.** Поля на верхнем уровне для
него нет, а без него монитор не ответит на вопрос «у скольких людей»: тысяча
отчётов от одного человека, который повторяет запрос, выглядит как тысяча
пострадавших. Поэтому `id` — то единственное поле `meta`, которое нельзя терять, и
поэтому `meta` держат крошечным: приёмник принимает его, только если
`JSON.stringify(meta)` не длиннее 8192 символов, а **превышение отбрасывает объект
целиком**, сохраняя `null` и отвечая при этом `200`. Наш `meta` занимает около
150 байт — запас в пятьдесят с лишним раз, и он сделан не из осторожности вообще, а
потому что цена превышения не «обрезали лишнее», а «потеряли идентификатор
установки молча».

**`message` не бывает пустым.** Правило отказа приёмника известно точно: `400`
возвращается тогда и только тогда, когда `message` пуст **и** `code` равен
`UNKNOWN`. Наш `message` никогда не пуст — при отсутствии текста подставляется вид
сбоя, — поэтому **от нашего плагина `400` недостижим**: ни одно сочетание полей,
которое способен собрать `reportPayload`, не удовлетворяет условию отказа. Это не
подстраховка на неизвестный случай, а доказуемое свойство отправляемой формы;
`400` остаётся в таблице ответов как ветка, которую плагин обрабатывает, но не
может вызвать.

**`model` — либо id из каталога провайдера, либо `unknown`.** Это не соглашение
оформления, а свойство приёмника: «вселенная» моделей в его картине строится как
каталог из `config.json` **плюс любой id, встретившийся в отчётах за период**. Id,
которого в каталоге нет, добавляется в картину отдельной строкой — с именем, равным
id, и с собственной доступностью, — и остаётся там, пока не истечёт срок хранения,
то есть до 45 дней. Один диагностический запрос с собственным именем модели стоит
публичному дашборду лишней строки на полтора месяца.

Наш запасной вариант совпадает с их собственным: отчёт, у которого модель определить
не удалось, уходит с `model: 'unknown'`, и ровно так приёмник называет отчёт без
поля `model` — строка «Без модели», общая для всех таких отчётов. Совпадение полезное:
безымянные отчёты не плодят строки, а складываются в одну.

### Пример

Запрос, построенный из реального сбоя: соединение с `rustvy.xyz:443` не
состоялось за десять секунд.

```http
POST /api/report HTTP/1.1
Host: 185.75.189.247:3789
Content-Type: application/json
User-Agent: dsh-rustvy
```

```json
{
  "plugin": "dsh-rustvy",
  "version": "1.0.0",
  "provider": "rustvy",
  "model": "gpt-6.1-sol",
  "code": "connect_timeout",
  "message": "Connect Timeout Error (attempted address: rustvy.xyz:443, timeout: 10000ms)",
  "ts": 1792435355423,
  "meta": {
    "id": "4f0a1c9e-7b2d-4e6a-9c31-8d5b2f7a0e14",
    "ms": 10683,
    "harnessCode": "TIMEOUT",
    "t": 1792435355423
  }
}
```

Поля `status` здесь нет: ответа не было вовсе. Тот же сбой у пользователя,
который повторил запрос пять раз за минуту, приходит одним отчётом — с числом
повторов и со статусом шлюза:

```json
{
  "plugin": "dsh-rustvy",
  "version": "1.0.0",
  "provider": "rustvy",
  "model": "gpt-6.1-sol",
  "code": "upstream_502",
  "status": 502,
  "message": "upstream_502 from the provider gateway while streaming",
  "ts": 1792435355423,
  "meta": {
    "id": "4f0a1c9e-7b2d-4e6a-9c31-8d5b2f7a0e14",
    "ms": 1290,
    "n": 5,
    "harnessCode": "PI_AI_ERROR",
    "t": 1792435355423
  }
}
```

`ts` и `meta.t` — момент **первого** из пяти событий, `meta.ms` — длительность
**последнего**, `meta.n` — сколько их было. Свёрнутый отчёт описывает начало окна,
а не его середину.

## Ответы приёмника и что делает плагин

Тела ответов взяты из `server.mjs` дословно.

| Ответ | Тело | Что делает плагин |
|---|---|---|
| `200` | `{"ok":true,"id":1792683213484}` | отчёт принят и забыт; откат сбрасывается |
| `400` | `{"ok":false,"error":"need a message or code field"}` | отчёт **отбрасывается** без повтора и считается потерянным |
| `429` | `{"ok":false,"error":"rate limit exceeded"}` | отчёт **остаётся в очереди**, следующая попытка откладывается |
| `503` | `{"ok":false,"error":"storage unavailable"}` | отчёт **остаётся в очереди**, следующая попытка откладывается |
| прочие `5xx`, сетевая ошибка, тайм-аут | — | то же: остаётся в очереди и откладывается |

`id` в успешном ответе — это `serverTs` сохранённого документа, то есть момент,
когда приёмник принял отчёт. Форма «похожа на миллисекунды» не случайно: это они и
есть. Это единственное подтверждение доставки, которое мы получаем, и по нему автор
приёмника может соотнести отчёт со своей строкой; плагин его не хранит, потому что
хранить нечего — отчёт уже удалён из очереди.

`503` возвращается, когда вставка в хранилище бросила исключение, и это единственный
ответ, который означает «приёмник жив, но записать не смог». Он повторяем, и плагин
повторяет.

**Предел тела — 64 КБ, и то, как приёмник сообщает о превышении, важнее самого
предела.** Тело запроса читается с пределом в **64 КБ** (`readJson(req, 65536, …)`).
Текущий Node-приёмник при превышении **уничтожает сокет, не отвечая вовсе**;
Go-приёмник отвечает честным `413` с телом. Два противоположных поведения, и разница
видна только в том, что происходит с очередью.

Уничтоженный сокет выглядит как сетевая ошибка, то есть как транспортный сбой, а
транспортный сбой у плагина повторяем. Отчёт, который не влез в предел, остался бы в
очереди навсегда, и, поскольку очередь отправляется по порядку, он задержал бы за
собой всё остальное: классическая блокировка головы очереди, которую не видно ни в
одном счётчике, кроме растущего `queued`. Честный `413` — это `4xx`, а любой `4xx`
кроме `429` у плагина отбрасывает один отчёт и продолжает со следующим, что ровно
правильно: тело, которое слишком велико, не станет меньше от ожидания.

Плагину не пришлось ничему учиться. Правило «`4xx` кроме `429` отбрасывает отчёт и
идёт дальше» было верным с самого начала и стало работать как задумано, когда сервер
перестал отвечать на превышение предела молчанием. Поэтому `413` не появляется в
таблице ответов выше отдельной строкой: не потому, что его не бывает, а потому, что
он не требует отдельной ветки.

До этого предела нам далеко, и расстояние стоит посчитать, потому что оно и есть
гарантия. Самое длинное поле — `message`, до 2000 символов; в худшем случае, когда
текст целиком кириллический, это около 6 КБ в UTF-8. Остальные поля обрезаны до 128
символов, `meta` — около 150 байт. Итого порядок 8 КБ против предела в 64 КБ, то есть
восьмикратный запас при самом неблагоприятном тексте. Плагин никогда не отправляет
тело, которое приёмник уничтожил бы не читая.

### `200` с предупреждением

Go-приёмник добавляет к успешному ответу необязательное поле `warnings` — массив
устойчивых строковых кодов в `lower_snake_case`, который присутствует, только когда
сказать есть что, так что обычный `200` остаётся байт в байт прежним `{ok, id}`:

```json
{ "ok": true, "id": 1792766000000, "warnings": ["meta_too_large"] }
```

Повод пока один, и он ровно тот, о котором этот документ предупреждал: `meta` больше
8192 символов отбрасывается **целиком**, вместе с `meta.id` — единственным полем,
отвечающим на вопрос «у скольких людей». Прежде приёмник делал это молча и отвечал
`200`, то есть отправитель узнавал о потере идентификатора установки только по тому,
что его отчёты переставали складываться в число пострадавших.

Правила поля:

- **ветвиться можно только по строке кода.** Незнакомый код потребитель игнорирует, а
  не считает ответ ошибочным, — иначе добавление кода ломает всех, кто поле читает;
- коды не переименовываются и не переиспользуются: новый повод — новый код;
- **прозы в поле нет вовсе.** Не потому, что пояснение не важно, а потому, что
  формулировка меняется при следующей правке и молча ломает всех, кто сопоставлял с
  ней, — а сопоставлять будут именно потому, что строка похожа на описание.

Чисел, ради которых прозу хотелось бы оставить, здесь нет, и это правильно: размер
своей `meta` отправитель может измерить сам — он единственный, у кого она есть, — так
что серверное пояснение не сообщило бы ему ничего нового. Числа при этом не потеряны:
коллектор пишет их в собственный журнал (`meta from <ip> is N bytes, over the M limit;
dropped whole, losing meta.id`), где их и найдёт оператор, которому нужно увидеть
плагин, постоянно превышающий предел.

**Предупреждение не отменяет успех.** Отчёт сохранён, поэтому `200` с `warnings` —
принятая отправка, и предупреждение принадлежит журналу или уведомлению, а не пути
повтора. Поле появляется только на `2xx`: предупреждение при отказе — часть отказа и
доходит до страницы настроек обычным путём, через строку `error`.

**Контракт требует, чтобы плагин это поле читал.** Формулировка контракта прямая:
отправка обязана прочитать предупреждение и сказать один раз (announce-once), назвав
отчёт, — иначе контракт описывает поле, которое никто не читает, а это хуже, чем поле
без него. Живёт это в половине хоста (`lib/host.js`), а не в `lib/errors.js`, потому
что именно хост владеет журналом и правилом «сказать один раз». На момент этой правки
ветка не реализована, и это расхождение с контрактом, а не приемлемая отсрочка.

Терпимость читателя направлена в одну сторону, и три её детали важны, потому что без
них реализация получается небезопасной. Знакомый строковый код читается как код.
Незнакомый строковый код проходит дальше как есть, а не считается ошибкой, — иначе
добавление кода ломает всех, кто поле читает. Элемент **не строкой** не разбирается и
не отбрасывается, а **печатается как есть**: приведённый к строке, с управляющими
символами, заменёнными пробелами, и обрезанный, — в той же строке журнала, что и
распознанные коды.

Почему правило именно такое, стоит записать, потому что обе очевидные замены хуже.
Разбирать чужую форму (читать `code` у объекта) значит писать код под форму, которую
никто не обещал: объект предлагали дважды и дважды отвергли, а сторонний коллектор
вправе назвать поле `type`, и тогда чтение `code` молча даст пустую строку — исход, от
которого правило защищает, только теперь за веткой, которая выглядит как обработка
случая. Считать нераспознанные элементы («было N нераспознанных предупреждений»)
значит выбросить содержание, которое коллектор всё-таки прислал. Печать как есть
дешевле обоих вариантов: имени поля она не предполагает, а содержание сохраняет.
Обрезка и замена управляющих символов — не украшение: строка журнала не должна
принимать произвольную длину и произвольные байты от удалённого сервиса.

Модулю отправки изменение не нужно, и это проверено, а не предполагается: приём в
`lib/errors.js` определяется как `status >= 200 && status < 300`, так что `200` с
`warnings` уже считается успешной отправкой — запись уходит из очереди, откат
сбрасывается. Ни ветка приёма, ни ветка отказа не читают тело на `2xx`, поэтому
предупреждение не может случайно стать повтором и не может случайно стать потерей.
Именно это делает поле бесплатным для каждого существующего отправителя.

Наш собственный `meta` занимает около 150 байт при пределе в 8192 символа, так что
`meta_too_large` нам не светит: запас пятидесятикратный. Но это не причина не
реализовывать читателя — предупреждение придёт от сторонних плагинов, которые
отправляют на тот же адрес.

Тело ответа читается в одном случае: при отказе `4xx` строка `error` из тела попадает
в `summary().lastError` дословно, как
`the collector answered 400: need a message or code field`. Это единственное
объяснение отброшенного отчёта, которое кто-либо когда-либо увидит, поэтому оно
сохраняется, а не пересказывается. Для `429` та же строка даёт
`the collector answered 429: rate limit exceeded` — и это полезно, потому что
отличает «приёмник занят» от «приёмник лежит» без обращения к его телу.

**Почему `429` — не отказ, а временная недоступность.** Прежняя логика «любой `4xx`
отбрасывает партию» для этого приёмника означала бы потерю настоящих отчётов
каждый раз, когда он занят: `429` говорит «слишком часто», а не «этот отчёт
непригоден». Пригодность выражает `400`. Отсюда деление: `429` и `5xx` —
повторяем, `400` и прочие `4xx` — отбрасываем. Отброшенный отчёт не будет принят
никогда, а отложенный будет принят, как только приёмник освободится. Код
приёмника подтверждает, что деление правильное: `429` возвращается **до** чтения
тела, то есть приёмник даже не смотрел на отчёт, и утверждать о нём что-либо не
может.

Если вместе с `429` пришёл `Retry-After`, плагин соблюдает его как нижнюю границу
паузы: ждёт `max(своя задержка, Retry-After)`, но не дольше собственного потолка
отката. Потолок нужен потому, что ошибочный или враждебный заголовок не должен
иметь возможность остановить отчётность на дни; ранняя попытка при `429` не стоит
ничего — отчёт остаётся в очереди. Сам приёмник `Retry-After` не присылает, так что
на практике работает собственное удвоение задержки.

## Частота и потолки

Приёмник допускает **60 отчётов в минуту на IP**, и он один на все установки
плагина. Ограничение реализовано как скользящее минутное окно: для каждого адреса
хранится список моментов запросов, из него выбрасывается всё старше минуты, и если
осталось 60 или больше — запрос отклоняется, не доходя до чтения тела. Число 60
берётся из `rateLimitPerMinute` в конфигурации приёмника, так что это настройка, а не
константа.

Адрес берётся из `x-forwarded-for`, если заголовок есть, — первое значение списка, —
иначе из адреса сокета. За обратным прокси это означает, что **все установки за одним
прокси считаются одним клиентом**, независимо от NAT. Один IP — это часто несколько
установок, и каждая из них тратит общую долю. Отсюда собственный потолок плагина
заметно ниже: установка, которая шлёт без ограничений, зарабатывает `429` не только
себе, но и соседям по адресу.

| Что | Значение | Следствие |
|---|---|---|
| Отчётов в одном сбросе | ≤ 10 | один POST на отчёт, последовательно, не параллельно |
| Отчётов в минуту на установку | ≤ 20 | треть лимита приёмника на одну установку |
| Отчётов в час на установку | ≤ 240 | жёсткий потолок; сверх него отчёты отбрасываются и считаются |
| Очередь в памяти | ≤ 500 отчётов | самое старое выбрасывается и считается потерянным |
| Таймер сброса | 15 с | не чаще одного прохода в 15 с |
| Тайм-аут отправки | 10 с | дольше приёмник держать запрос не может |
| Откат после сбоя | 15 с → 30 с → … → 600 с | пока приёмник лежит, это 6–12 запросов в час |
| Окно свёртки ошибок | 60 с | один отчёт на пару «модель + вид» в минуту |
| Запись на диск | не чаще раза в 5 с | очередь переживает перезапуск |

Минутный потолок **не теряет** отчёты: когда он исчерпан, остаток просто ждёт
следующей минуты и уходит со своими исходными `ts`. Часовой — теряет, и это
единственное место, где отчёты выбрасываются намеренно; счётчик `dropped` делает
это видимым вместо загадочного.

**Спокойный режим**, когда всё работает: ноль отчётов. Ошибок нет — отправлять
нечего, и это главная экономия против зонда.

**Авария**: один отчёт на пару «модель + вид» в минуту, то есть 60 в час на модель,
плюс метка восстановления. Одна лежащая модель даёт 60 отчётов в час; потолок в
240 ограничивает любую установку сверху, что бы ни происходило.

**Авария самого приёмника** — отдельный случай, и он важнее остальных: пока он не
отвечает, отчёты дойти не могут, поэтому плагин уходит в откат до 10 минут и держит
отчёты в очереди (до 500) и на диске. Нагрузка в этот момент почти нулевая, а после
восстановления приходит пачка с метками времени из прошлого. Абсолютный худший
случай на установку — 240 POST-запросов в час; реалистичный — единицы.

## Словарь `code`

Полный набор значений, которые плагин кладёт в поле `code`. Всё, что отмечено как
«отправляется», — единственное, что приёмник увидит в отчётах.

| `code` | Отправляется | Что означает |
|---|---|---|
| `connect_timeout` | да | соединение не установилось за отведённое время, `ETIMEDOUT` |
| `timeout` | да | ответ не пришёл или поток замер: любой другой тайм-аут, включая `LLM_STREAM_IDLE_TIMEOUT` |
| `dns` | да | имя не разрешилось: `ENOTFOUND`, `EAI_AGAIN`, `getaddrinfo` |
| `refused` | да | соединение отклонено: `ECONNREFUSED` |
| `reset` | да | соединение оборвано: `ECONNRESET`, `EPIPE`, `socket hang up`, `other side closed`, `premature close` |
| `unreachable` | да | маршрута нет: `ENETUNREACH`, `EHOSTUNREACH`, `no route to host` |
| `tls` | да | сертификат или рукопожатие: `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, `DEPTH_ZERO_SELF_SIGNED_CERT`, `ERR_TLS_*` |
| `http_5xx` | да | шлюз или сервер ответил 5xx: `http_500`, `http_502`, `http_503`, `http_504` |
| `http_404`, `http_408` | да | модель или путь исчезли, либо запрос не успел; остальные `http_4xx` **не** отправляются |
| `upstream_NNN` | 5xx, 400, 404, 408 — да | так шлюз провайдера назвал ответ собственного апстрима: `upstream_502`, `upstream_503`, `upstream_400`, `upstream_404` |
| `server` | да | код `SERVER` без статуса |
| `transport` | да | сетевая ошибка общего вида, `fetch failed` |
| `unknown` | да | код способен описывать сбой инфраструктуры, но текст не распознан |
| `upstream_401`, `upstream_402`, `upstream_403`, `upstream_429` | нет | апстрим ответил про аутентификацию, оплату или лимит — это положение пользователя |
| `quota` | нет | квота, кредиты или баланс исчерпаны |
| `billing` | нет | подписка, оплата, задолженность, заблокированный аккаунт |
| `auth` | нет | ключ неверен, отсутствует или истёк; `401`, `403` |
| `rate_limit` | нет | `429`, too many requests |
| `context` | нет | контекст не поместился |
| `model` | нет | модель неизвестна или не поддерживается |
| `aborted` | нет | запрос прервал пользователь |
| `request` | нет | ошибка самого запроса или конфигурации: `INVALID_REQUEST`, `EMPTY_RESPONSE`, `NO_ADAPTER` и подобные коды harness |

**Почему 404 и 408 — это про сервис, а остальные 4xx — про отправителя.** Шлюз,
ответивший 404 на просьбу маршрутизировать модель, сообщает факт о себе: такого
маршрута у него нет. 408 — то же по смыслу: запрос не успел дойти до конца, и это
состояние пути, а не содержимого запроса. Остальные 4xx описывают вызывающую
сторону: 400 — запрос собран неверно, 401 и 403 — ключ не годится, 429 — она шлёт
слишком часто. Различие не формальное, и оно нужно читателю дашборда: строка
`http_404` в картине — ожидаемый трафик от шлюза, у которого нет маршрута, а не
признак того, что классификация плагина сломана. Правило действует с первой версии
модуля и с тех пор не менялось.

Растущая доля `unknown` — сигнал, что словарь отстал от жизни: появился новый текст
сбоя, и его стоит превратить в отдельный вид. Для монитора `unknown` — такой же
сбой, как остальные.

## Что никогда не отправляется

В отчёте нет и не может появиться: текста запросов и ответов модели, содержимого
сообщений и файлов, API-ключей и любых других секретов, идентификаторов чатов и
сессий, имён пользователей и учётных записей, абсолютных путей на машине
пользователя и имён их машин.

Текст ошибки — единственное поле, которое приходит извне, и оно проходит через
`scrubErrorText` перед тем, как попасть в отчёт. Гарантии, которые можно считать
контрактом:

- схлопываются пробелы и переводы строк;
- удаляются ключи вида `sk-…`, значения `Bearer`, значения именованных полей
  (`api_key`, `token`, `authorization`, `client_secret`, …) и заголовки с учётными
  данными — вместо них `<key>`, `Bearer <redacted>`, `<secret>`, `<header>`;
- абсолютные пути Windows (включая UNC `\\server\share\…`) и POSIX заменяются на
  `<path>` **целиком**, в том числе когда в имени каталога есть пробел:
  `C:\Users\…\Programs\DeepSeek Harness\profiles\desktop` уходит как `<path>`, а не
  как `<path> Harness\profiles\desktop`. Пробел пересекается только тогда, когда за
  ним в пределах 60 символов встречается разделитель пути, — поэтому
  `failed to open C:\foo bar baz qux and then the stream ended` теряет лишь `C:\foo`
  и сохраняет остаток фразы;
- непрозрачные последовательности длиннее 40 символов (base64, JWT, дампы)
  заменяются на `<blob>`;
- результат обрезается до 2000 символов — потолка самого приёмника;
- адрес провайдера в тексте **сохраняется**: `rustvy.xyz:443` — не данные
  пользователя, а единственная подсказка о том, что именно не отвечало.

Все шаблоны ограничены по длине, а входной текст обрезается до 4000 символов до
обработки: сообщение приходит от внешнего сервиса через адаптер и считается
враждебным, поэтому катастрофический backtracking на нём исключён.

Единственное псевдонимное значение в отчёте — **uuid установки** в `meta.id`. Он
создаётся один раз при первом запуске и лежит в
`<profile>\.dsh-rustvy\install.json`. Сброс — удалить этот файл: следующий запуск
создаст новый uuid, и установка станет для монитора другим человеком. Сборка
отчётов выключается целиком настройкой «Собирать ошибки rustvy» или переменной
окружения; выключенный репортёр не считает ничего и не отправляет ничего.

## Что значит uptime без записей об успехах

Успехи не уходят на провод, поэтому доступность модели — это **отсутствие отчётов
об ошибках** в окне, а не доля зелёных записей среди всех. Приёмник считает её ровно
так, и формулу можно прочитать в его `buildView`:

```js
uptime = errors === 0 ? 100 : +(100 * (48 - downSlots) / 48).toFixed(1)
status = errors === 0 ? 'up' : (uptime >= 50 ? 'slow' : 'down')
```

где `downSlots` — число корзин из 48, в которых есть хотя бы одна ошибка. Три
следствия, которые читатель картины должен знать: это доля **свободных от ошибок
окон**, а не доля успешных запросов (приёмник не знает, сколько было запросов); одна
ошибка за сутки даёт 97,9 %; а `down` требует ошибок более чем в половине корзин,
то есть обычное состояние «что-то случилось» — это `slow`, а не `down`. Полный разбор
— в [docs/uptime-view.md](<uptime-view.md>).

**Доля доступности.** На интервале считаются отчёты с данным `model`. Ноль отчётов
— модель отвечала; интервал, в котором модель никто не спрашивал, выглядит точно
так же, и различить их можно только по другим моделям того же провайдера в том же
интервале: отчёты по одной модели при молчании остальных — это авария одной модели,
а общее молчание — скорее всего отсутствие трафика. У приёмника эта неоднозначность
разрешается в пользу «всё хорошо»: модель без отчётов получает честные 100 %,
независимо от того, падала ли она молча или её просто не спрашивали.

**Сколько людей.** Число различных `meta.id` на интервале. Без uuid установки
тысяча отчётов от одного человека, который повторяет запрос, выглядит как тысяча
пострадавших; с ним — как один. Обратная сторона: удаление `install.json` создаёт
новый uuid, поэтому счётчик людей за длинный интервал слегка завышен.

**Границы аварии.** Первый отчёт по данной модели — начало. Конец виден по тому,
что отчёты перестали приходить; точную метку восстановления даёт приход свёрнутого
отчёта сразу после успеха — плагин отправляет его в тот момент, когда модель снова
ответила, а не по окончании окна.

**Длительность и глубина.** Разность `ts` между первым и последним отчётом серии —
длительность аварии; сумма `meta.n` — сколько попыток она стоила пользователям;
`meta.ms` — последняя длительность запроса; `status` отличает «шлюз ответил 502» от
«соединение не состоялось вовсе» (поля `status` нет); `code` говорит, где именно
сломалось.

**Что считать аварией.** Одиночный отчёт от одной установки — ещё не авария: у
одного человека мог оборваться Wi-Fi. Устойчивое правило — несколько различных
`meta.id` с одним `code` в одном интервале; сам порог — на усмотрение автора
монитора, данные для него здесь есть.

## `ts` может быть намного старше доставки

Свёртка не заканчивается вместе с процессом. Очередь и ещё не закрытые окна
записываются на диск (`<profile>\.dsh-rustvy\errors-queue.json`) и читаются обратно
при следующем запуске, поэтому отчёт приезжает со своим исходным `ts` и с тем
`meta.n`, которое успело накопиться, — даже если между двумя половинами окна плагин
был перезагружен. На практике это выглядит так: окно собрало `n: 22`, половина
плагина перезагрузилась, и после перезагрузки тот же отчёт доехал до приёмника —
при том что счётчики у нового экземпляра начинаются с нуля и показывают меньше, чем
`meta.n`. Это не расхождение, а одно и то же окно, разделённое перезагрузкой.

**Что с этим делает приёмник сейчас — и это важно знать читателю картины.** Наш `ts`
сохраняется в документе как `clientTs`, но агрегация его не использует: `list()`
проектирует наружу `serverTs` под именем `t`, и именно по нему `buildView` раскладывает
отчёты по корзинам и сортирует события. То есть картина строится **по времени
получения, а не по времени события**.

Для отчёта, который дошёл сразу, разницы нет. Для отчёта из очереди она ровно та,
которую описывает этот раздел: авария, длившаяся три часа и доставленная одним пакетом
после восстановления, ложится в корзины момента доставки и выглядит как короткий
всплеск там, где были три часа проблем. Оценить масштаб расхождения можно по разности
`serverTs − clientTs` — она лежит в каждом документе и показывает, какая доля отчётов
приезжает опоздавшей и насколько.

Правильная группировка — по `clientTs`, и данные для неё сохранены; не хватает только
того, чтобы `list()` их отдавал. Это отдельная правка на стороне приёмника, и она
независима от той, что чинит пустую картину: даже когда отчёты начнут находиться,
картина останется построенной по времени доставки, пока агрегация не начнёт
использовать `clientTs`.

И `meta.n` — число событий внутри окна отчёта, а не за время жизни одного процесса,
поэтому сравнивать его со счётчиками плагина в `/state` не нужно.

Возможен и повтор: если процесс завершился между принятым отчётом и записью очереди
на диск, тот же отчёт уйдёт ещё раз. Дедупликация по `(meta.id, ts, model, code)`
закрывает и это.

## Адрес

`http://185.75.189.247:3789/api/report` — публичный приёмник и адрес по умолчанию в
плагине. Он общий: на него отправляют отчёты все установки плагина, а не одна, и
именно поэтому потолки частоты из раздела выше — не вежливость, а необходимость:
много установок, один приёмник, и одна установка, которая шлёт без ограничений,
портит картину всем остальным.

Открытый HTTP по голому IP — осознанное решение на данный момент, а не недосмотр.
Отчёт по содержанию публичен и обезличен (см. «Что никогда не отправляется»), поэтому
шифрование защищает не тайну, а целостность и подлинность; как только появится
доменное имя и сертификат, адрес стоит сменить на `https`. Выпуска для этого не
нужно: настройка `uptimeEndpoint` в `<profile>\.dsh-rustvy\config.json` и переменная
окружения `DSH_RUSTVY_UPTIME_ENDPOINT` перенаправляют отчёты на любой адрес, причём
адрес перечитывается перед каждой отправкой, а не запоминается при монтировании.
Переменная окружения важнее настройки, но обе проходят проверку на разборчивый
http-адрес: значение, которое не разбирается, отбрасывается, и в силе остаётся
предыдущее. Значит перенаправить или заглушить отчёты можно, а прислать плагину
мусор вместо адреса — нет.

Тот же `uptimeEndpoint` ведёт и читательскую половину: плагин берёт из него начало
адреса и путь `/api/view`, а ссылкой на монитор служит то же начало с путём `/`.
Подробности — в [docs/uptime-view.md](<uptime-view.md>).

Приёмник уже переезжал, и контракт от этого не изменился: на новом адресе наш запрос
с нашим телом возвращает `200 {"ok":true,"id":1792683213484}`, `GET /api/health`
отвечает `200 {"ok":true,"storage":"mongo"}`, а `GET /` отдаёт страницу «rustvy
uptime». Форму ответа при переезде не меняли, так что вся таблица ответов выше
описывает поведение боевого адреса, а не стенда.

Формат, словарь `code`, поведение на кодах ответа и потолки уже реализованы и
меняются только вместе с версией плагина, которая уходит в поле `version`.

### Куда приёмник кладёт отчёт

Хранилище выбирается один раз при запуске: MongoDB, если в конфигурации задан
`mongo.uri` (или переменная `MONGODB_URI`) **и** соединение установилось за отведённые
5 секунд; иначе файловое хранилище в `data/errors.json` с записью, отложенной на
400 мс. Какое из двух работает, видно без отправки отчёта — `GET /api/health`
отвечает `{"ok":true,"storage":"mongo"}` или `{"ok":true,"storage":"file"}`, и то же
значение приезжает в поле `storage` ответа `/api/view`.

Для отправителя это диагностически важнее, чем кажется, и не в ту сторону, в которую
подсказывает слово «fallback»: именно файловое хранилище работает правильно, а
MongoDB — то, которое принимает отчёты и не находит их при чтении (причина разобрана
в [docs/uptime-view.md](<uptime-view.md>)). Значит `storage: "file"` на развёрнутом
экземпляре означает «Mongo не поднялся, но данные читаются», а `storage: "mongo"` —
«данные пишутся и не читаются».

Срок хранения — 45 дней по `serverTs`, но обрезка выполняется **только в файловом
хранилище**, которое фильтрует строки при каждом сохранении. В MongoDB не удаляется
ничего: ни одной команды удаления в его коде нет, хотя их README обещает 45 дней в
обоих случаях. Отправителю это ничего не меняет — отчёт принимается одинаково, — но
оценивать объём накопленного по документации приёмника не стоит.
