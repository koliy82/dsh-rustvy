# Отчёты об ошибках: контракт с `POST /api/report`

Приёмник существует и отвечает; всё, что описано ниже, проверено запросами к нему,
а не взято из предположений. Документ описывает две половины одного провода: что
приёмник принимает и как плагин (`lib/errors.js`, `lib/net.js`) заполняет его поля.
Автору монитора достаточно этого файла — читать исходник плагина не нужно.

Адрес по умолчанию: `http://185.75.189.247:8249/api/report` — общий публичный
приёмник, один на все установки. Метод `POST`,
`content-type: application/json`, тело — **один плоский объект**. Конверта и массива
событий нет: один отчёт — один POST.

## Зачем это существует

Монитору нужно три факта: **когда** модель перестала отвечать, **у скольких людей**
одновременно и **что именно** сломалось. Обычный способ их получить — зонд:
отдельный запрос к модели по расписанию. У зонда две беды: он сжигает токены на
запросы, которые никому не нужны, и он отвечает за одного человека — за того, на
чьей машине запущен, поэтому «сайт лежит» и «у меня не работает» для него
неразличимы.

Вместо зонда используются **пассивные отчёты**. Плагин и так знает исход каждого
запроса к модели, который сделал пользователь, и сообщает только о сбоях
инфраструктуры. Один сбой — один отчёт, в котором есть момент, модель, вид сбоя,
статус, длительность и очищенный текст ошибки.

Отсюда два следствия, важных для приёмника. Отчёты приходят **пачками и задним
числом**: всякий раз, когда отправить не удалось — приёмник занят или лежит, машина
пользователя не в сети или спала, — отчёты накапливаются в очереди на диске и после
восстановления приезжают разом, со своими исходными метками времени, которым может
быть несколько часов или дней. Приёмник при этом живёт не там же, где API
провайдера, поэтому авария провайдера сама по себе не мешает отчётам дойти; мешают
ей только собственный простой приёмника и отсутствие сети у пользователя. И отчёты
**не требуют аутентификации**: плагин не отправляет ни ключей, ни заголовка
`Authorization` никогда.

## Что отправляется и когда

**Ошибка** отправляется только тогда, когда она инфраструктурная: соединение не
состоялось, DNS не разрешился, сокет отказал или оборвался, TLS не собрался, шлюз
провайдера ответил 5xx или 404, ответ не пришёл за отведённое время. Решение
принимает `classifyFailure`, и оно же отвечает за то, чего в отчёте не будет вовсе:
кончившаяся подписка, исчерпанная квота или баланс, неверный либо отсутствующий
ключ, rate limit, не поместившийся контекст, прерванный пользователем запрос,
неизвестная модель и любая другая ошибка запроса, которую harness помечает
собственным кодом. Это положение конкретного пользователя, а не состояние сервиса,
и в мониторе оно выглядело бы как авария на ровном месте.

**Успех не отправляется никогда.** Приёмник принимает ошибки, и успешный запрос —
не событие для него. Успех выполняет две локальные задачи: считается для страницы
настроек, чтобы было видно, что плагин жив и смотрит, а не молча простаивает, и
немедленно отправляет ещё не закрытую свёрнутую ошибку той же модели. Именно
второе даёт монитору метку восстановления: отчёт о сбое приезжает в момент, когда
модель снова ответила, а не по окончании окна свёртки.

Отправка не блокирует запрос и не может его уронить: очередь живёт в памяти и на
диске, таймер не держит процесс, а любая ошибка внутри отчётности проглатывается.

## Поля приёмника

Все поля необязательны, кроме одного правила: должно присутствовать хотя бы
`message` или `code`. У большинства полей есть синонимы — это варианты одного
хранимого столбца, а не дополнительные поля.

| Поле (синонимы) | Тип | Смысл |
|---|---|---|
| `message` (`error`, `detail`) | string | текст ошибки, до **2000** символов |
| `code` (`type`, `kind`) | string | тип ошибки; при отсутствии приёмник подставляет `UNKNOWN` |
| `plugin` (`source`) | string | какой плагин прислал |
| `version` | string | версия плагина |
| `provider`, `model` | string | провайдер и модель, где применимо |
| `status` | int | HTTP-статус, **если он есть** |
| `ts` (`timestamp`) | number | время клиента в миллисекундах; приёмник в любом случае ставит свой `serverTs` |
| `meta` | object | произвольные дополнительные данные, до **8 КБ** |

Неизвестные поля на верхнем уровне приёмник игнорирует и отвечает `200`, так что
добавление поля в будущем не сломает доставку.

## Как плагин их заполняет

Один синоним на понятие, всегда. Плагин отправляет `message`, `code`, `plugin`,
`ts` и никогда не отправляет рядом `error`, `detail`, `type`, `kind`, `timestamp`
или `source`: если прислать два варианта одного столбца, выбирать, какой из них
хранить, придётся приёмнику.

| Поле приёмника | Значение плагина |
|---|---|
| `plugin` | `dsh-rustvy`, всегда |
| `version` | версия плагина из `package.json` |
| `provider` | маршрут провайдера: `rustvy`, `rustvy-k2`, … |
| `model` | id модели; `unknown`, если определить не удалось |
| `code` | **наш вид сбоя** (`connect_timeout`, `upstream_502`, …) — см. ниже |
| `status` | HTTP-статус; **поле отсутствует**, когда статуса не было |
| `message` | очищенный текст ошибки, до 2000 символов; никогда не пустой |
| `ts` | момент события в миллисекундах, а не момент отправки |
| `meta.id` | uuid установки |
| `meta.ms` | длительность запроса в миллисекундах |
| `meta.n` | сколько событий свёрнуто в отчёт; отсутствует, когда одно |
| `meta.harnessCode` | код ошибки, каким его дал harness |
| `meta.t` | тот же момент события, что и `ts` |

Четыре решения стоит объяснить отдельно.

**В `code` — наш вид сбоя, а не код harness.** Монитор группирует по вопросу
«какие ошибки падали на данной модели», и `upstream_502` на него отвечает, а
`PI_AI_ERROR` — нет: под этим кодом одинаково живут и отказ соединения, и ответ
шлюза, и оборванный поток. Вердикт harness при этом не теряется, он переезжает в
`meta.harnessCode`. Если автору приёмника нужна в `code` собственная таксономия —
в его примере стоит `INVALID_REQUEST`, то есть как раз код harness, — замена
делается в одну строку в `reportPayload`, и строка помечена комментарием.

**`status` отсутствует, а не равен нулю.** В контракте написано «если есть», и `0`
не является HTTP-статусом: у тайм-аута соединения статуса просто нет. Приёмник
принимает и отсутствующее поле, и `0` — оба дают `200`, — так что это выбор
читаемости, а не требование. Он всё же сделан, потому что ноль в столбце с типом
«HTTP-статус» кто-нибудь однажды агрегирует. Длительность при этом не теряется:
она лежит в `meta.ms`.

**`meta.id` — единственное место для uuid установки.** Поля на верхнем уровне для
него нет, а без него монитор не ответит на вопрос «у скольких людей»: тысяча
отчётов от одного человека, который повторяет запрос, выглядит как тысяча
пострадавших. Поэтому `id` — то единственное поле `meta`, которое нельзя терять.
Весь объект занимает около 150 байт при потолке в 8 КБ.

**`message` не бывает пустым.** Пустой текст при непустом `code` проходит правило
приёмника («хотя бы одно из двух») и даёт `200`, но отчёт без текста бесполезен для
того, кто будет его читать, — поэтому вместо пустого текста подставляется вид
сбоя. Проверено, что это подстраховка: `code` без `message` и `message` без `code`
принимаются одинаково.

### Пример

Запрос, построенный из реального сбоя: соединение с `rustvy.xyz:443` не
состоялось за десять секунд.

```http
POST /api/report HTTP/1.1
Host: 185.75.189.247:8249
Content-Type: application/json
User-Agent: dsh-rustvy
```

```json
{
  "plugin": "dsh-rustvy",
  "version": "1.0.0",
  "provider": "rustvy",
  "model": "gpt-6.1-sol",
  "code": "connect_timeout",
  "message": "Connect Timeout Error (attempted address: rustvy.xyz:443, timeout: 10000ms)",
  "ts": 1792435355423,
  "meta": {
    "id": "4f0a1c9e-7b2d-4e6a-9c31-8d5b2f7a0e14",
    "ms": 10683,
    "harnessCode": "TIMEOUT",
    "t": 1792435355423
  }
}
```

Поля `status` здесь нет: ответа не было вовсе. Тот же сбой у пользователя,
который повторил запрос пять раз за минуту, приходит одним отчётом — с числом
повторов и со статусом шлюза:

```json
{
  "plugin": "dsh-rustvy",
  "version": "1.0.0",
  "provider": "rustvy",
  "model": "gpt-6.1-sol",
  "code": "upstream_502",
  "status": 502,
  "message": "upstream_502 from the provider gateway while streaming",
  "ts": 1792435355423,
  "meta": {
    "id": "4f0a1c9e-7b2d-4e6a-9c31-8d5b2f7a0e14",
    "ms": 1290,
    "n": 5,
    "harnessCode": "PI_AI_ERROR",
    "t": 1792435355423
  }
}
```

`ts` и `meta.t` — момент **первого** из пяти событий, `meta.ms` — длительность
**последнего**, `meta.n` — сколько их было. Свёрнутый отчёт описывает начало окна,
а не его середину.

## Ответы приёмника и что делает плагин

Ответы приведены дословно, как их вернул приёмник.

| Ответ | Тело | Что делает плагин |
|---|---|---|
| `200` | `{"ok":true,"id":1792683213484}` | отчёт принят и забыт; откат сбрасывается |
| `400` | `{"ok":false,"error":"need a message or code field"}` | отчёт **отбрасывается** без повтора и считается потерянным |
| `429` | — | отчёт **остаётся в очереди**, следующая попытка откладывается |
| `503` | — | отчёт **остаётся в очереди**, следующая попытка откладывается |
| прочие `5xx`, сетевая ошибка, тайм-аут | — | то же: остаётся в очереди и откладывается |

`id` в успешном ответе — идентификатор записи на стороне приёмника, по форме
похожий на миллисекунды. Это единственное подтверждение доставки, которое мы
получаем, и по нему автор приёмника может соотнести отчёт со своей строкой; плагин
его не хранит, потому что хранить нечего — отчёт уже удалён из очереди.

Тело ответа больше не читается нигде, кроме одного случая: при отказе `4xx` строка
`error` из тела попадает в `summary().lastError` дословно, как
`the collector answered 400: need a message or code field`. Это единственное
объяснение отброшенного отчёта, которое кто-либо когда-либо увидит, поэтому оно
сохраняется, а не пересказывается.

**Почему `429` — не отказ, а временная недоступность.** Прежняя логика «любой `4xx`
отбрасывает партию» для этого приёмника означала бы потерю настоящих отчётов
каждый раз, когда он занят: `429` говорит «слишком часто», а не «этот отчёт
непригоден». Пригодность выражает `400`. Отсюда деление: `429` и `5xx` —
повторяем, `400` и прочие `4xx` — отбрасываем. Отброшенный отчёт не будет принят
никогда, а отложенный будет принят, как только приёмник освободится.

Если вместе с `429` пришёл `Retry-After`, плагин соблюдает его как нижнюю границу
паузы: ждёт `max(своя задержка, Retry-After)`, но не дольше собственного потолка
отката. Потолок нужен потому, что ошибочный или враждебный заголовок не должен
иметь возможность остановить отчётность на дни; ранняя попытка при `429` не стоит
ничего — отчёт остаётся в очереди.

## Частота и потолки

Приёмник допускает **60 отчётов в минуту на IP**, и он один на все установки
плагина. Лимит считается по адресу отправителя, а не по установке, поэтому один IP
— это часто несколько установок за одним NAT, и каждая из них тратит общую долю.
Отсюда собственный потолок плагина заметно ниже: установка, которая шлёт без
ограничений, зарабатывает `429` не только себе, но и соседям по адресу.

| Что | Значение | Следствие |
|---|---|---|
| Отчётов в одном сбросе | ≤ 10 | один POST на отчёт, последовательно, не параллельно |
| Отчётов в минуту на установку | ≤ 20 | треть лимита приёмника на одну установку |
| Отчётов в час на установку | ≤ 240 | жёсткий потолок; сверх него отчёты отбрасываются и считаются |
| Очередь в памяти | ≤ 500 отчётов | самое старое выбрасывается и считается потерянным |
| Таймер сброса | 15 с | не чаще одного прохода в 15 с |
| Тайм-аут отправки | 10 с | дольше приёмник держать запрос не может |
| Откат после сбоя | 15 с → 30 с → … → 600 с | пока приёмник лежит, это 6–12 запросов в час |
| Окно свёртки ошибок | 60 с | один отчёт на пару «модель + вид» в минуту |
| Запись на диск | не чаще раза в 5 с | очередь переживает перезапуск |

Минутный потолок **не теряет** отчёты: когда он исчерпан, остаток просто ждёт
следующей минуты и уходит со своими исходными `ts`. Часовой — теряет, и это
единственное место, где отчёты выбрасываются намеренно; счётчик `dropped` делает
это видимым вместо загадочного.

**Спокойный режим**, когда всё работает: ноль отчётов. Ошибок нет — отправлять
нечего, и это главная экономия против зонда.

**Авария**: один отчёт на пару «модель + вид» в минуту, то есть 60 в час на модель,
плюс метка восстановления. Одна лежащая модель даёт 60 отчётов в час; потолок в
240 ограничивает любую установку сверху, что бы ни происходило.

**Авария самого приёмника** — отдельный случай, и он важнее остальных: пока он не
отвечает, отчёты дойти не могут, поэтому плагин уходит в откат до 10 минут и держит
отчёты в очереди (до 500) и на диске. Нагрузка в этот момент почти нулевая, а после
восстановления приходит пачка с метками времени из прошлого. Абсолютный худший
случай на установку — 240 POST-запросов в час; реалистичный — единицы.

## Словарь `code`

Полный набор значений, которые плагин кладёт в поле `code`. Всё, что отмечено как
«отправляется», — единственное, что приёмник увидит в отчётах.

| `code` | Отправляется | Что означает |
|---|---|---|
| `connect_timeout` | да | соединение не установилось за отведённое время, `ETIMEDOUT` |
| `timeout` | да | ответ не пришёл или поток замер: любой другой тайм-аут, включая `LLM_STREAM_IDLE_TIMEOUT` |
| `dns` | да | имя не разрешилось: `ENOTFOUND`, `EAI_AGAIN`, `getaddrinfo` |
| `refused` | да | соединение отклонено: `ECONNREFUSED` |
| `reset` | да | соединение оборвано: `ECONNRESET`, `EPIPE`, `socket hang up`, `other side closed`, `premature close` |
| `unreachable` | да | маршрута нет: `ENETUNREACH`, `EHOSTUNREACH`, `no route to host` |
| `tls` | да | сертификат или рукопожатие: `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, `DEPTH_ZERO_SELF_SIGNED_CERT`, `ERR_TLS_*` |
| `http_5xx` | да | шлюз или сервер ответил 5xx: `http_500`, `http_502`, `http_503`, `http_504` |
| `http_404`, `http_408` | да | модель или путь исчезли, либо запрос не успел; остальные `http_4xx` **не** отправляются |
| `upstream_NNN` | 5xx, 400, 404, 408 — да | так шлюз провайдера назвал ответ собственного апстрима: `upstream_502`, `upstream_503`, `upstream_400`, `upstream_404` |
| `server` | да | код `SERVER` без статуса |
| `transport` | да | сетевая ошибка общего вида, `fetch failed` |
| `unknown` | да | код способен описывать сбой инфраструктуры, но текст не распознан |
| `upstream_401`, `upstream_402`, `upstream_403`, `upstream_429` | нет | апстрим ответил про аутентификацию, оплату или лимит — это положение пользователя |
| `quota` | нет | квота, кредиты или баланс исчерпаны |
| `billing` | нет | подписка, оплата, задолженность, заблокированный аккаунт |
| `auth` | нет | ключ неверен, отсутствует или истёк; `401`, `403` |
| `rate_limit` | нет | `429`, too many requests |
| `context` | нет | контекст не поместился |
| `model` | нет | модель неизвестна или не поддерживается |
| `aborted` | нет | запрос прервал пользователь |
| `request` | нет | ошибка самого запроса или конфигурации: `INVALID_REQUEST`, `EMPTY_RESPONSE`, `NO_ADAPTER` и подобные коды harness |

Растущая доля `unknown` — сигнал, что словарь отстал от жизни: появился новый текст
сбоя, и его стоит превратить в отдельный вид. Для монитора `unknown` — такой же
сбой, как остальные.

## Что никогда не отправляется

В отчёте нет и не может появиться: текста запросов и ответов модели, содержимого
сообщений и файлов, API-ключей и любых других секретов, идентификаторов чатов и
сессий, имён пользователей и учётных записей, абсолютных путей на машине
пользователя и имён их машин.

Текст ошибки — единственное поле, которое приходит извне, и оно проходит через
`scrubErrorText` перед тем, как попасть в отчёт. Гарантии, которые можно считать
контрактом:

- схлопываются пробелы и переводы строк;
- удаляются ключи вида `sk-…`, значения `Bearer`, значения именованных полей
  (`api_key`, `token`, `authorization`, `client_secret`, …) и заголовки с учётными
  данными — вместо них `<key>`, `Bearer <redacted>`, `<secret>`, `<header>`;
- абсолютные пути Windows (включая UNC `\\server\share\…`) и POSIX заменяются на
  `<path>` **целиком**, в том числе когда в имени каталога есть пробел:
  `C:\Users\…\Programs\DeepSeek Harness\profiles\desktop` уходит как `<path>`, а не
  как `<path> Harness\profiles\desktop`. Пробел пересекается только тогда, когда за
  ним в пределах 60 символов встречается разделитель пути, — поэтому
  `failed to open C:\foo bar baz qux and then the stream ended` теряет лишь `C:\foo`
  и сохраняет остаток фразы;
- непрозрачные последовательности длиннее 40 символов (base64, JWT, дампы)
  заменяются на `<blob>`;
- результат обрезается до 2000 символов — потолка самого приёмника;
- адрес провайдера в тексте **сохраняется**: `rustvy.xyz:443` — не данные
  пользователя, а единственная подсказка о том, что именно не отвечало.

Все шаблоны ограничены по длине, а входной текст обрезается до 4000 символов до
обработки: сообщение приходит от внешнего сервиса через адаптер и считается
враждебным, поэтому катастрофический backtracking на нём исключён.

Единственное псевдонимное значение в отчёте — **uuid установки** в `meta.id`. Он
создаётся один раз при первом запуске и лежит в
`<profile>\.dsh-rustvy\install.json`. Сброс — удалить этот файл: следующий запуск
создаст новый uuid, и установка станет для монитора другим человеком. Сборка
отчётов выключается целиком настройкой «Собирать ошибки rustvy» или переменной
окружения; выключенный репортёр не считает ничего и не отправляет ничего.

## Что значит uptime без записей об успехах

Успехи не уходят на провод, поэтому доступность модели — это **отсутствие отчётов
об ошибках** в окне, а не доля зелёных записей среди всех.

**Доля доступности.** На интервале считаются отчёты с данным `model`. Ноль отчётов
— модель отвечала; интервал, в котором модель никто не спрашивал, выглядит точно
так же, и различить их можно только по другим моделям того же провайдера в том же
интервале: отчёты по одной модели при молчании остальных — это авария одной модели,
а общее молчание — скорее всего отсутствие трафика.

**Сколько людей.** Число различных `meta.id` на интервале. Без uuid установки
тысяча отчётов от одного человека, который повторяет запрос, выглядит как тысяча
пострадавших; с ним — как один. Обратная сторона: удаление `install.json` создаёт
новый uuid, поэтому счётчик людей за длинный интервал слегка завышен.

**Границы аварии.** Первый отчёт по данной модели — начало. Конец виден по тому,
что отчёты перестали приходить; точную метку восстановления даёт приход свёрнутого
отчёта сразу после успеха — плагин отправляет его в тот момент, когда модель снова
ответила, а не по окончании окна.

**Длительность и глубина.** Разность `ts` между первым и последним отчётом серии —
длительность аварии; сумма `meta.n` — сколько попыток она стоила пользователям;
`meta.ms` — последняя длительность запроса; `status` отличает «шлюз ответил 502» от
«соединение не состоялось вовсе» (поля `status` нет); `code` говорит, где именно
сломалось.

**Что считать аварией.** Одиночный отчёт от одной установки — ещё не авария: у
одного человека мог оборваться Wi-Fi. Устойчивое правило — несколько различных
`meta.id` с одним `code` в одном интервале; сам порог — на усмотрение автора
монитора, данные для него здесь есть.

## `ts` может быть намного старше доставки

Свёртка не заканчивается вместе с процессом. Очередь и ещё не закрытые окна
записываются на диск (`<profile>\.dsh-rustvy\errors-queue.json`) и читаются обратно
при следующем запуске, поэтому отчёт приезжает со своим исходным `ts` и с тем
`meta.n`, которое успело накопиться, — даже если между двумя половинами окна плагин
был перезагружен. На практике это выглядит так: окно собрало `n: 22`, половина
плагина перезагрузилась, и после перезагрузки тот же отчёт доехал до приёмника —
при том что счётчики у нового экземпляра начинаются с нуля и показывают меньше, чем
`meta.n`. Это не расхождение, а одно и то же окно, разделённое перезагрузкой.

Для приёмника отсюда два следствия. Группировать нужно строго по `ts`, а не по
`serverTs`: одна и та же авария приходит пачкой, в которой отчёты разнесены по
часам, и группировка по времени приёма размажет её. Разница `serverTs − ts` при
этом полезна сама по себе — по ней видно, какая доля отчётов приезжает опоздавшей,
и она же отличает настоящую аварию от массового перезапуска очередей. И `meta.n` —
число событий внутри окна отчёта, а не за время жизни одного процесса, поэтому
сравнивать его со счётчиками плагина в `/state` не нужно.

Возможен и повтор: если процесс завершился между принятым отчётом и записью очереди
на диск, тот же отчёт уйдёт ещё раз. Дедупликация по `(meta.id, ts, model, code)`
закрывает и это.

## Адрес

`http://185.75.189.247:8249/api/report` — публичный приёмник и адрес по умолчанию в
плагине. Он общий: на него отправляют отчёты все установки плагина, а не одна, и
именно поэтому потолки частоты из раздела выше — не вежливость, а необходимость:
много установок, один приёмник, и одна установка, которая шлёт без ограничений,
портит картину всем остальным.

Открытый HTTP по голому IP — осознанное решение на данный момент, а не недосмотр.
Отчёт по содержанию публичен и обезличен (см. «Что никогда не отправляется»), поэтому
шифрование защищает не тайну, а целостность и подлинность; как только появится
доменное имя и сертификат, адрес стоит сменить на `https`. Выпуска для этого не
нужно: настройка `uptimeEndpoint` в `<profile>\.dsh-rustvy\config.json` и переменная
окружения `DSH_RUSTVY_UPTIME_ENDPOINT` перенаправляют отчёты на любой адрес, причём
адрес перечитывается перед каждой отправкой, а не запоминается при монтировании.
Переменная окружения важнее настройки, но обе проходят проверку на разборчивый
http-адрес: значение, которое не разбирается, отбрасывается, и в силе остаётся
предыдущее. Значит перенаправить или заглушить отчёты можно, а прислать плагину
мусор вместо адреса — нет.

Тот же `uptimeEndpoint` ведёт и читательскую половину: плагин берёт из него начало
адреса и путь `/api/view`, а ссылкой на монитор служит то же начало с путём `/`.
Подробности — в [docs/uptime-view.md](<uptime-view.md>).

Приёмник уже переезжал, и контракт от этого не изменился: на новом адресе наш запрос
с нашим телом возвращает `200 {"ok":true,"id":1792683213484}`, `GET /api/health`
отвечает `200 {"ok":true,"storage":"mongo"}`, а `GET /` отдаёт страницу «rustvy
uptime». Форму ответа при переезде не меняли, так что вся таблица ответов выше
описывает поведение боевого адреса, а не стенда.

Формат, словарь `code`, поведение на кодах ответа и потолки уже реализованы и
меняются только вместе с версией плагина, которая уходит в поле `version`.
