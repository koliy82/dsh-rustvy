# Аптайм моделей: контракт с `GET /api/view`

Приёмник, которому плагин отправляет отчёты об ошибках, — тот же сервер, с которого
он читает статус назад. Этот документ описывает вторую половину провода: `GET
/api/view`, что в ответе лежит, как его рисует собственный монитор приёмника и что
плагин (`lib/uptime.js`) делает с ответом перед тем, как отдать его настройкам.

Всё ниже **наблюдено**, а не выведено: ответы сняты живыми запросами к
`http://185.75.189.247:8249`, а правила отрисовки прочитаны в исходнике их страницы
мониторинга по адресу `/` (заголовок «rustvy uptime»). Там, где правило взять
неоткуда, это сказано прямо — таких полей три, и они перечислены в разделе про
известный дефект.

## Запрос

```http
GET /api/view?range=24h HTTP/1.1
Host: 185.75.189.247:8249
Accept: */*
User-Agent: dsh-rustvy
```

`range` обязан быть одним из трёх значений, и это whitelist самого приёмника, а не
предпочтение плагина:

| `range` | Период | Ширина одной корзины |
|---|---|---|
| `24h` | сутки | 30 минут |
| `7d` | неделя | 3,5 часа |
| `30d` | месяц | 15 часов |

На любое другое значение приёмник отвечает:

```http
400
{"error":"range must be one of: 24h, 7d, 30d"}
```

Поэтому `isUptimeRange` проверяется **до** запроса: неверный диапазон отклоняется
локально и не тратит ни обращения к сети, ни строки в логе.

## Ответ

Верхний уровень:

| Поле | Тип | Смысл |
|---|---|---|
| `generatedAt` | int, epoch ms | когда приёмник собрал ответ |
| `range` | string | период, за который собран ответ |
| `storage` | string | хранилище приёмника, наблюдалось `mongo` |
| `healthy` | bool | живо ли хранилище |
| `total` | int | ошибок за период; их же печатает подвал их страницы как «ошибок: N» |
| `summary` | object | шесть счётчиков, см. ниже |
| `byCode` | array | разбивка по кодам; их собственная страница её не читает |
| `models` | array | по одной записи на модель, в порядке приёмника |

`summary`:

| Поле | Тип | Смысл |
|---|---|---|
| `totalModels` | int | сколько моделей в каталоге приёмника |
| `operational` | int | сколько из них в состоянии `up` |
| `slow` | int | сколько в состоянии `slow` |
| `down` | int | сколько в состоянии `down` |
| `uptime` | number, 0..100 | доступность в процентах |
| `totalErrors` | int | всего ошибок за период |

Одна запись `models`:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | string | id модели; совпадает с id в каталоге провайдера, например `claude-opus-5-5` |
| `name` | string | отображаемое имя, например `OPUS 5.5` |
| `errors` | int | ошибок у этой модели за период |
| `uptime` | number, 0..100 | доступность модели в процентах |
| `status` | string | `up`, `slow` или `down` |
| `buckets` | array | ровно 48 корзин `{ from: epoch ms, count: int }` — для любого периода |
| `events` | array | `{ t: epoch ms, code, status?, message?, plugin? }` |
| `lastError` | object \| null | `{ t: epoch ms, code, message }` либо `null` |

## Сорок восемь корзин

Корзин всегда 48, независимо от периода. Отсюда следствие, которое легко
не заметить: **ширина корзины меняется вместе с периодом**, и одна и та же полоска
из 48 столбиков означает получасовые интервалы на `24h`, трёхчасовые на `7d` и
пятнадцатичасовые на `30d`. Подпись под полоской обязана это отражать, иначе
неделя, на которой модель лежала полдня, выглядит как неделя с одной тонкой
царапиной.

Плагин не дополняет массив до 48 и не пересчитывает его: клиент рисует то, что
пришло, и масштабирует по фактической длине. Всё, что нужно для отрисовки, даёт
`bucketStats`:

| Поле | Смысл |
|---|---|
| `count` | сколько корзин пришло |
| `max` | наибольшее значение в одной корзине, **не меньше 1** |
| `first`, `last` | крайние метки `from`, либо `null`, если корзин нет |
| `errors` | сумма всех `count` |

`max` не бывает нулём — полоска из пустых корзин масштабируется относительно
единицы, а не делит на ноль. Это правило их страницы (`max(1, …counts)`), а не
изобретение плагина.

## Как это рисует их собственная страница

Правила приведены потому, что плагин и веб-монитор показывают одни и те же данные
одному и тому же человеку. Два экрана, которые расходятся в цвете или в подписи,
стоят дороже, чем один некрасивый: пользователь, увидевший «Degraded» на сайте и
жёлтую точку в настройках, имеет право знать, что это одно и то же.

| `status` | Подпись | Бейдж | Цвет |
|---|---|---|---|
| `up` | «Operational» | «UP» | `#22c55e` |
| `slow` | «Degraded» | «SLOW» | `#f59e0b` |
| `down` | «Down» | «DOWN» | `#ef4444` |

Полоска корзин масштабируется по `max(1, …counts)`. Последняя ошибка печатается как
«последняя ошибка <время> — <код> <сообщение>» с относительной подписью
«только что», «N мин назад», «N ч назад», «N дн назад». Подвал страницы читается
«период: <range> · ошибок: <total> · хранилище: <storage>» и «обновлено
<generatedAt>». Их страница обновляется сама каждые 30 секунд.

## Что плагин делает с ответом

Ответ приходит с удалённого сервера и рисуется в браузере, поэтому считается
враждебным по умолчанию. `normalizeUptimeView` возвращает один из двух вариантов, и
вызывающая сторона смотрит только на `ok`:

```js
{ ok: true, range, generatedAt, healthy, storage, total, summary, byCode, models }
{ ok: false, error: '<фраза по-русски>' }
```

Отказ возможен ровно в трёх случаях: ответ не объект, в ответе нет массива `models`,
и ответ не удалось разобрать вовсе. Всё остальное **чинится, а не отбраковывается**:
модель с испорченным процентом доступности всё равно стоит показать строкой, а вот
строку, которую невозможно опознать, показывать не стоит.

Правила по полям:

- `range` — только из whitelist, иначе `24h`. Значение, которого приёмник не
  присылал, не должно доехать до подписи «период: …».
- `generatedAt`, `total` и все счётчики `summary` — целые неотрицательные, при
  отсутствии ноль; `uptime` зажимается в 0..100.
- `healthy` — `false` только если приёмник сказал `false` явно. Отсутствие поля не
  означает болезнь: ответ пришёл, модели в нём есть.
- `storage` — строка до 128 символов, при отсутствии пустая.
- `byCode` — передаётся **как есть**, если это массив (копия, до 100 элементов),
  иначе пустой массив. Их собственная страница его не читает, поэтому придумывать
  ему форму здесь означало бы придумывать контракт, которого никто не заключал.
- `id` модели обязателен: запись без него выпадает из массива. `name` при отсутствии
  становится равным `id`, так что каталог без отображаемых имён всё равно рисуется.
  Порядок моделей сохраняется — он приходит от приёмника.
- `status` приводится к нижнему регистру и сверяется с тройкой; **всё незнакомое
  становится `up`**.
- `buckets` не дополняются до 48. Запись без числового `from` выпадает: у неё нет
  места на оси времени, и придуманное место было бы ложью. Отсутствующий `count` —
  это ноль, то есть спокойная корзина, и приёмник такие присылает.
- `events` и `lastError` читаются строже всего остального — см. раздел про дефект.
  Запись события без числового `t` выпадает; `status` сохраняется только когда это
  настоящий HTTP-статус (100..599), потому что ноль нарисовался бы статусом и не
  значил бы ничего; необязательные поля **отсутствуют**, а не приходят пустыми
  строками. `lastError` становится `null`, если у него нет числового `t` или нечего
  напечатать.

**Почему незнакомый статус — это `up`, а не `down`.** Незнакомый статус означает
пробел в знании плагина, а не состояние модели. Если приёмник завтра добавит
четвёртое состояние или ответит опечаткой, цена ошибки несимметрична: угадав `down`,
плагин покажет рабочую модель красной человеку, который по этому экрану решает,
доверять ли провайдеру, — а статусная страница, которая врёт в красную сторону,
перестаёт быть статусной страницей. Угадав `up`, плагин теряет одну зелёную точку.
Красный оставлен за тем, что приёмник действительно назвал красным.

**Потолки.** Ответ рисуется в браузере, поэтому ни один массив не проходит
насквозь: не больше 50 моделей, 200 корзин на модель (приходит ровно 48), 25
событий на модель, 100 элементов `byCode`, сообщение события до 500 символов,
прочие строки до 128. Наблюдаемые из этих чисел — «ровно 48 корзин на модель» и
«12 моделей в каталоге приёмника»: на `185.75.189.247:8249` ответ пришёл с
`summary` `{totalModels: 12, operational: 12, slow: 0, down: 0, uptime: 100,
totalErrors: 0}`. Остальное выбрано как кратный запас, а не как оценка: размер
каталога — не константа, поэтому потолок в 50 моделей оставляет место росту, а не
подогнан под одно наблюдение.

Важен не каждый потолок по отдельности, а их произведение: сбойный или щедрый
приёмник умножает модели на корзины на события на длину сообщения. При этих
значениях худший ответ, который модуль способен вернуть, — около 1,3 МБ JSON, то
есть то, что браузер переживёт. Обычный зелёный ответ определяется почти целиком
корзинами — порядка килобайта на модель — и остаётся на два порядка меньше.

Модуль ничего не бросает в вызывающую сторону ни при каком входе: все четыре
публичные функции защищены, в том числе от объекта с бросающим геттером. Тело,
разобранное из JSON, такого содержать не может, — и обещание намеренно не зависит от
того, что вызывающая сторона принесёт именно его.

## Известный дефект приёмника

**Агрегация приёмника не видит ни одного отчёта, который он принял.**

Это свойство приёмника, а не одного адреса, и проверка пережила переезд.

Первое наблюдение, на прежнем адресе: приёмнику отправлено одиннадцать отчётов, и
каждый принят — `200 {"ok":true,"id":…}`. Четыре из них отправлены непосредственно
перед проверкой и покрывают четыре разные формы: код harness (`INVALID_REQUEST`
вместе со `status: 400`), наш вид сбоя (`upstream_502` вместе со `status: 502`),
отчёт вовсе без `model` и отчёт вовсе без `ts`. После этого `GET /api/view` на всех
трёх периодах отвечал `total: 0` и `summary.totalErrors: 0`, пустым `byCode`, ни
одной ненулевой корзины и ни одного события; ответ был перечитан через две минуты,
чтобы исключить задержку индексации.

Второе наблюдение, уже на `http://185.75.189.247:8249`: отчёт отправлен и принят
(`200 {"ok":true,"id":1792683213484}`), и `GET /api/view?range=24h` по-прежнему
отвечает `total: 0`, `summary.totalErrors: 0`, `byCode: []`, без событий и без
единой ненулевой корзины — при двенадцати моделях и сорока восьми корзинах у каждой.

**Отсюда главное: путь записи и путь чтения расходятся независимо от того, куда они
направлены.** Переезд не изменил ничего, значит дело не в конкретном развёртывании,
не в индексах одного экземпляра и не в адресе, а в том, что принятый отчёт не
попадает в то, что читает `/api/view`. Это единственное предложение раздела, которое
нужно тому, кто будет чинить API; остальное — следствия для плагина.

Первое следствие: поля `events`, `byCode` и `lastError` **никогда не наблюдались
заполненными**. Их форма известна только из JavaScript их собственной страницы
мониторинга. Поэтому они и читаются строже остальных, и поэтому их отсутствие — не
ошибка разбора, а норма.

Второе следствие: **пустой зелёный ответ — это обычный ответ, а не вырожденный**.
Именно его увидит каждый пользователь первым, и именно его должна честно рисовать
страница настроек: «ошибок: 0», все модели зелёные, ни одной последней ошибки. Плагин
терпит этот дефект, а не обходит его — он не досчитывает ничего от себя, не подменяет
данные приёмника собственными локальными счётчиками и не выдаёт догадку за
наблюдение. Локальные счётчики (`/state`) и данные приёмника описывают разные вещи:
первые — эту установку, вторые — всех сразу, и смешивать их на одном экране значит
показывать человеку число, которое не означает ни того, ни другого.

Для того, кто будет чинить агрегацию: формы всех трёх полей уже зафиксированы
здесь, так что исправление на стороне приёмника не потребует выпуска плагина —
заполненные `events`, `byCode` и `lastError` доедут до настроек как есть.

## `/api/health` — дешёвая проверка доступности

```http
GET /api/health
200 {"ok":true,"storage":"mongo"}
```

Этот запрос стоит использовать там, где нужно отличить «приёмник недоступен» от
«приёмник работает, но ошибок нет»: он дешевле `/api/view` и не несёт никаких
данных о моделях. Важно, что он **не** говорит об агрегации: живой и здоровый
приёмник по-прежнему отвечает `total: 0` при принятых отчётах, так что `ok: true`
нельзя читать как «данные есть».

## Адрес

Отдельной настройки для чтения нет: все три адреса выводятся из одного
`uptimeEndpoint`, в котором лежит адрес **отправки** отчётов. По умолчанию это
`http://185.75.189.247:8249/api/report`, и из него получается:

| Что | Как выводится | Адрес по умолчанию |
|---|---|---|
| отправка отчётов | `uptimeEndpoint` как есть | `http://185.75.189.247:8249/api/report` |
| чтение статуса | то же начало, путь заменяется на `/api/view` | `http://185.75.189.247:8249/api/view` |
| ссылка на монитор | то же начало плюс `/` | `http://185.75.189.247:8249/` |

Отсюда два полезных свойства. Одна правка настройки перенаправляет отправку, чтение
и ссылку на монитор одновременно, и они не могут разъехаться. И порт в примере — не
часть контракта: вывод работает от разобранного адреса, поэтому переезд приёмника на
другой хост и порт ничего не ломает. Это не предположение — приёмник уже переезжал,
и форма ответов от переезда не изменилась.

Настройка `uptimeEndpoint` в `<profile>\.dsh-rustvy\config.json` и переменная
окружения `DSH_RUSTVY_UPTIME_ENDPOINT` перенаправляют всё это без выпуска; адрес
перечитывается, а не запоминается при монтировании. Переменная окружения важнее
настройки, но обе проходят проверку на разборчивый http-адрес: значение, которое не
разбирается, отбрасывается, и в силе остаётся предыдущее. Сам вывод адресов живёт в
половине хоста (`lib/host.js`); в `lib/uptime.js` работы с адресами нет вовсе, и
модуль проверяет только `range`.

Открытый HTTP по голому IP — осознанное решение на данный момент, по той же
причине, что и в [docs/error-report.md](<error-report.md>): данные публичны и
обезличены, поэтому шифрование защищает здесь целостность и подлинность, а не
тайну. Как только появятся домен и сертификат, все три адреса стоит перевести на
`https` одной правкой настройки.
