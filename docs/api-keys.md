# API-ключи: контракт между половинами

Рабочий контракт для host- и браузерной половин. Всё, что здесь написано, уже
согласовано с тем, как устроен harness этой версии (`0.2.1-rc.2`); ссылки на
внутренности приведены, чтобы правка одной половины не ломала другую.

## Что должно получиться для пользователя

1. Ключ добавляется в самом плагине, кнопкой **«+»**: значение и необязательное
   название. Никакой правки `.env`, `cordis.patch.yml` или страницы Models.
2. Выбор ключа для чата — в одном месте: компактный переключатель в панели
   композера, сразу справа от списка режимов доступа («Read only / Workspace
   Write / Full access»). Меню выбора модели раздела ключей **не** получает —
   вместо этого декоратор прячет дублирующие группы провайдеров-клонов, чтобы
   один и тот же список моделей не повторялся по разу на каждый ключ.
3. Выбор действует **только на этот чат** и сохраняется между перезапусками.
4. Учётная запись DeepSeek не затрагивается: подмена касается только маршрутов
   этого плагина и никогда — `deepseek-account` / `deepseek-official`.

## Как ключ доходит до запроса

`@deepseek-ai/dsh-llm-pi-ai` берёт ключ так
(`dsh-llm-pi-ai/lib/index.js:2893-2900`):

```js
const ref = profile.apiKeyEnv                       // имя, не значение
const hit = (await ctx.get('credentials').resolve(ref))?.value
```

`LlmCallConfig` и `GenerateOptions` поля для ключа не имеют, а `baseURL` и
`headers` пекутся в снапшот профиля. Поэтому один маршрут = один ключ, и
единственный честный способ дать чату другой ключ — **другой маршрут** с тем же
`api`/`baseURL`/`models` и своим `apiKeyEnv`.

Отсюда устройство:

| Слой | Что делает |
|---|---|
| `credentials.set(ref, value)` | хранит значение ключа в `$DSH_HOME/.credentials.yaml`, раздел `refs`. Плагин значения в своих файлах не держит |
| `keys.json` (плагин) | метаданные: `id`, `label`, `ref`, `route`, `primary`, `createdAt`, `order`, и `defaultKeyId` |
| `configEditor.edit('llm-pi-ai')` | дописывает в `providers` по одному маршруту на каждый дополнительный ключ |
| `session-keys.json` (плагин) | `sessionId → keyId`, переживает перезапуск |
| `ctx.on('agent/request')` | подменяет `provider` у запроса на маршрут выбранного ключа — тот же приём, которым harness применяет выбор модели (`dsh-agent/lib/index.js:182-193`) |

`resolveApiKey` вызывается на каждый запрос, а не кешируется, поэтому смена
значения ключа действует со следующего запроса без перезапуска. Смена *имени*
(`apiKeyEnv`) требует перезаписи конфигурации — плагин её и делает.

Первый ключ всегда остаётся основным: он владеет маршрутом из профиля
(`rustvy`) и его собственным `apiKeyEnv` (`RUSTVY_API_KEY`). Дополнительные
получают `RUSTVY_API_KEY_2`, `RUSTVY_API_KEY_3`, … и маршруты `rustvy-k2`,
`rustvy-k3`, …

Подмена в `agent/request` срабатывает только когда все условия сошлись:

- переключатель `apiKeys` включён, а в кольце больше одного ключа;
- у запроса есть сессия (`payload.agent.session.id`);
- действующий ключ — собственный выбор чата из `session-keys.json`, иначе ключ
  по умолчанию, — и он не основной: основной и есть маршрут профиля, его
  переименовывать некуда;
- `provider` запроса — один из наших маршрутов (`rustvy`, `rustvy-k*`);
- целевой маршрут установлен в конфигурации и отдаёт запрошенную модель.

Во всех остальных случаях конфиг возвращается как пришёл, а исключение внутри
подмены перехватывается: запрос уходит дальше нетронутым. Запросы DeepSeek Account
идут через провайдер `deepseek-account` и под условие не попадают вовсе.

Если целевой маршрут не установлен или не отдаёт эту модель, запрос остаётся на
маршруте профиля, а причина попадает в `fallback` на `/keys` и одним предупреждением
в журнал — шаг не падает из-за ключа, но и молча не проходит.

## Маршруты host-половины

Все — под префиксом `/dsh-rustvy`, с той же проверкой собеседника
(`refusalOf`), что и остальные: только loopback, только same-origin.

### `GET /keys`

```jsonc
{
  "ok": true,
  "enabled": true,            // настройка «ключи на несколько чатов»
  "credentials": true,        // смонтирован ли сервис credentials
  "editor": true,             // доступен ли configEditor (без него маршрут не добавить)
  "route": "rustvy",          // основной маршрут из настроек
  "entryId": "llm-pi-ai",
  "packageName": "@deepseek-ai/dsh-llm-pi-ai",
  "baseURL": "https://rustvy.xyz/v1",
  "modelsUrl": "https://rustvy.xyz/v1/models",
  "defaultKeyId": "k1",
  "maxKeys": 12,
  "keys": [
    {
      "id": "k1",
      "label": "Основной",
      "ref": "RUSTVY_API_KEY",
      "route": "rustvy",
      "displayName": "rustvy",
      "primary": true,
      "present": true,        // значение есть в credentials
      "masked": "sk-…f8",     // только для показа
      "fingerprint": "9f2c1a7b",
      "createdAt": "2026-10-19T15:00:00.000Z",
      "installed": true,      // маршрут ключа есть в профиле
      "models": 12,           // сколько моделей отдаёт этот маршрут
      "sessions": 3           // сколько чатов выбрали этот ключ
    }
  ],
  "hiddenGroups": ["rustvy · ключ 2"],  // displayName маршрутов, которые не для выбора руками
  "routes": { "missing": [], "stale": [] },
  "routing": { "seen": 41, "applied": 7 },
  "picks": 3,
  "paths": { "keys": "…\\.dsh-rustvy\\keys.json", "picks": "…\\.dsh-rustvy\\session-keys.json" },
  "fallback": null,
  "error": null
}
```

Значения ключей не отдаются никогда: ни целиком, ни по частям. `masked` — первые
три и последние два символа, `fingerprint` — короткий отпечаток, чтобы две
записи с одним значением можно было узнать, не читая его.

`routes.missing` — ключи, чей маршрут из профиля пропал (ручная правка
`cordis.patch.yml`, откат списка моделей): на это страница отвечает кнопкой
**«Починить маршруты»**. `routes.stale` — маршруты, чей список моделей отстал от
сгенерированного; лечится уже имеющейся кнопкой **«Записать список моделей»**.

`routing.seen` — сколько запросов harness вообще провёл через водопад
`agent/request`, `routing.applied` — сколько из них были переименованы на маршрут
ключа. `seen === 0` при живом трафике означает, что водопад не доходит до плагина,
и это видно сразу, а не по тому, что ключи «не работают».

`fallback` — последний запрос, который **не** ушёл выбранным ключом, потому что
его маршрут не установлен или не отдаёт эту модель. Запрос при этом не падает: он
уходит маршрутом из профиля, а причина показывается на странице.

### `POST /keys`

Одно тело на все действия; успешный ответ — свежий `GET /keys` плюс поле
результата, поэтому один POST перерисовывает всё. Отказ — HTTP 409 с
`{ ok: false, error }` (неизвестное действие — 400); текст на русском, он
показывается как есть.

| `action` | Поля | Что делает |
|---|---|---|
| `add` | `key`, `label?` | новый ключ: `credentials.set`, запись в `keys.json`, маршрут в конфигурации. `{ added: id }` |
| `set` | `id`, `key` | заменить значение существующего ключа; конфигурации не касается. `{ updated: id }` |
| `rename` | `id`, `label` | название, и вместе с ним `displayName` маршрута. `{ updated: id }` |
| `default` | `id` | ключ по умолчанию для новых чатов. `{ defaultKeyId: id }` |
| `remove` | `id` | убрать ключ: маршрут из конфигурации, `credentials.unset`, записи сессий с него сбрасываются на ключ по умолчанию. Основному ключу отказывает — `{ ok: false, error }` |
| `repair` | — | записать маршруты кольца заново, для профиля, который их потерял. `{ added, removed, updated }` |
| `test` | `id` | `GET {baseURL}/models` с этим ключом. `{ test: { id, ok, status, models, error } }` |

Ошибки — `{ ok: false, error: "…" }` с кодом HTTP 400/409/500; текст на русском,
он показывается как есть.

### `GET /session-key?sessionId=<id>`

```jsonc
{ "ok": true, "sessionId": "…", "keyId": "k2", "picked": true,
  /* и целиком весь ответ GET /keys: keys, hiddenGroups, routes, routing, … */ }
```

`keyId` — ключ, которым этот чат шлёт запросы: его собственный выбор, иначе ключ по
умолчанию, иначе основной. `picked` — есть ли у чата собственный выбор.

### `POST /session-key`

`{ "sessionId": "…", "keyId": "k2" }` → тот же payload, что и `GET`.
`keyId: null` сбрасывает чат на ключ по умолчанию. Выбор, равный ключу по
умолчанию, не запоминается: в файле лежат только отклонения, поэтому чат,
созданный до смены defaults, следует за ними.

## Что рисует браузерная половина

Две поверхности выбора/управления и одно декоративное действие в меню модели:

1. **Страница настроек → Rustvy**, раздел «API-ключи»: список ключей (название,
   маска, ref, маршрут, сколько чатов его используют), кнопка **«+»** с
   инлайн-формой «название + значение», у каждой строки — заменить значение,
   переименовать, назначить ключом по умолчанию, проверить, удалить.
2. **Композер**: регистрация в слоте `conversation.input.left`
   (`id: 'rustvy-key'`, `order: 60`), то есть в панели инструментов сразу после
   списка режимов доступа. Компактная кнопка с названием активного ключа и меню:
   список ключей с галочкой, строка «по умолчанию» и строка **«+ Добавить ключ»**
   с той же инлайн-формой. Компонент получает `sessionId` в standard props слота.
3. **Меню выбора модели**: раздел ключей сюда **не** добавляется. Декоратор
   только прячет группы провайдеров из `hiddenGroups` (клоны маршрутов), чтобы
   один и тот же список моделей не показывался по разу на каждый ключ. Скрытие
   структурное и осторожное: заголовок группы опознаётся по тексту из
   `hiddenGroups`, и если уверенности нет — не прячется ничего, потому что
   скрыть настоящую строку модели хуже, чем оставить дубль группы.

`sessionId` знает только поверхность 2: компонент композера пишет его в состояние
декоратора при монтировании. Скрытие групп (пункт 3) от сессии не зависит.

Состояние читается с `GET /session-key` при монтировании переключателя и после
каждого выбора; список ключей кешируется между поверхностями и обновляется по
событию `dsh-rustvy:changed`, которое страница настроек уже рассылает.

## Границы

- Нет `credentials` — добавление ключа недоступно, интерфейс говорит почему.
- Нет `configEditor` — то же: значение записать можно, маршрут добавить нельзя.
- Ключ один — переключатель в композере не рисуется вовсе (выбирать нечего), а
  меню модели и так не получает раздела ключей.
- Плагин выключен (`DSH_RUSTVY_DISABLED=1` или настройка) — подмена не
  устанавливается, маршруты ключей остаются в конфигурации, но не используются.
